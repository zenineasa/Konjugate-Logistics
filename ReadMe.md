# Konjugate Logistics Toolbox

A logistics extension for [Konjugate](https://github.com/zenineasa/Konjugate), the open-source, graph-native simulation engine. It models how goods move from suppliers and ports through warehouses to stores and customers, on the vehicles that carry them, as stocks and flows that Konjugate integrates over time.

## Status

Early development. Where it is going: [docs/direction.md](docs/direction.md) (a general supply network, milestones A to H; the first two, sites with roles on a map and their links, are built as [docs/mapFirst.md](docs/mapFirst.md) describes). Picking up the work: [docs/handover.md](docs/handover.md). What exists today:

- a component library plugin, `konjugate.logistics.engine`, with one example model, verified end to end against a real Konjugate build;
- the **Logistics Toolbox** add-on (`konjugate.logistics.toolbox`), whose window loads the roads of any city or region, lets the user place a supply network on them (suppliers, ports, warehouses, stores, dark stores and customer areas, with the links between them, each site's storage and stock cover, and the vehicles each link runs on) and builds a runnable model from it. Ports, warehouses and towns found in public data are suggestions the user asks for and adopts, never added on their own.

## What's in the component library

| Component | Kind | What it models |
|---|---|---|
| Port | node | Ships waiting at anchorage and a container yard. Vessels arrive at a steady rate; the berths handle them up to their capacity, which can drop during an outage window. Reports how long a ship waits. |
| Road lane | node | A trucking lane between two sites: containers on the road (an Erlang-3 travel time), and a fleet of trucks in up to two sizes, each idle, loaded or returning empty. Loading is limited by idle trucks, shared between the sizes by their idle capacity, and each size is hired towards a target. An open share (1 normally, 0 while the road is closed) scales the loading. Tracks utilisation, transport cost per kilometre and fleet cost per truck-day, for each size. |
| Rail lane | node | A rail link with a fixed number of trains a day. Containers on the line travel with an Erlang-3 travel time; tracks transport cost per TEU. |
| Warehouse | node | On-hand stock, what is on order across its lanes, a demand forecast by exponential smoothing, and an order rate set by an order-up-to rule. It aims for its stock cover target, or its storage capacity if that is less, and never orders towards more than it has room for; goods already on their way still arrive, so **Space used** (stock over capacity) shows when it overflows. Tracks holding cost. A store's stock room is a Warehouse too. |
| Demand zone | node | Customers ordering at a steady rate, with an optional demand step. Tracks the backlog, its cost, and running totals of what was ordered and delivered. |
| Road shipment | bundle | Connects an origin (a port or a warehouse), a road lane and a destination warehouse. Orders go to the lane; the origin ships what the lane's idle trucks of both sizes can carry and its stock allows; loaded trucks arrive at the destination and return empty. |
| Rail shipment | bundle | The same for a rail lane, limited by the trains' capacity instead of trucks. |
| Store shipment | bundle | A road shipment from a warehouse to a store's stock room, which also feeds the store's orders into the warehouse's demand forecast, as a delivery feeds a demand zone's. |
| Delivery | bundle | Ships from a warehouse to a demand zone and clears the same amount from the zone's backlog, optionally serving the zone only while the warehouse holds more than a set level. Also feeds the zone's demand back to the warehouse's forecast. When several warehouses serve one zone, each takes its share of the zone's demand. |

Place nodes by clicking them in Konjugate's component library. To apply a bundle, select its endpoint nodes (a port and a warehouse, or a warehouse and a demand zone), then click the bundle. A shipment bundle takes three: the origin, the lane and the destination.

Every edge that moves containers (dispatch, arrival and delivery) is bidirectional, so what leaves one node enters the next, and containers are conserved by construction. So are trucks: each road lane's idle, loaded and returning trucks always add up to its fleet. Order signals, backlog clearing and the demand signal are directed edges: they update order books and forecasts, not stock. States such as the order rate, what a lane can load, and a ship's waiting time are algebraic: set from the node's other states rather than integrated.

**Units.** The templates count in TEU (twenty-foot equivalent units); a network placed in the toolbox window counts pallets instead, with the same equations, a port's containers counting as ten pallets each (an assumption to adjust). Simulation time `t` is in seconds, as everywhere in Konjugate. Rates are entered per day and divided by one shared `secondsPerDay` parameter, so a 120-day run has a target time of 120 × 86400 s.

**Shared parameters.** Quantities that belong to one node or lane are created per placement, so each warehouse has its own lead time and each lane its own share. You can change them in the parameters table, and in a fork once you make them live. Model-wide constants, such as a truck's capacity, the cost per kilometre, the berthing time and the outage window, are one definition shared by every component that uses them. A model the toolbox builds from a network with vehicle types makes each type's capacity, costs and loading time one definition of its own (`miniVanCapacity`, say), shared by every lane and shipment the type runs on, so a lane's two sizes can be any two types.

## Example

**Port and warehouse network** appears in Konjugate's Examples dialog once the plugin is installed. A port feeds two warehouses over two road lanes, serving three customer zones. The baseline is balanced and holds still. The guide that comes with it forks the run at day 10 to take most of the berths out for a month, so ships queue at anchorage, and to step up demand, so the trucks become the bottleneck until the fleet grows. The model is generated from the templates by `scripts/buildModels.mjs`, and its guide is `guides/portWarehouseNetwork.md`.

## The Logistics Toolbox window

Open it from the **Logistics** button on Konjugate's toolstrip. Nothing in it is written for a particular place.

1. **Load the roads.** Search a place name (OpenStreetMap's Nominatim), choose how far around it to include, and whether to load **major roads** (motorways, trunk and primary roads, for a region up to 250 km across) or **city streets too** (secondary and tertiary roads as well, where stores and dark stores are, for an area up to 40 km across). **Load roads** asks OpenStreetMap's Overpass API for the roads and place names alone, one request at a time, in tiles no wider than 40 km (10 km for city streets); a tile too large or too slow is fetched again in quarters, and a busy public server is retried after a pause, waiting longer when its status page says no slot is free (up to about ten minutes per request). Nothing else is fetched. What is fetched is kept on this computer (in Konjugate's cache for the add-on, kept when the add-on is reinstalled or updated and removed with it), so the same area loads again at once and offline, and the window says when its roads were fetched; data kept more than 30 days is fetched again, **Load fresh** fetches everything again now, and **Clear** at the foot of the Map step removes the kept maps. The map shows the roads and the names of places, as many as stay readable: cities always, towns, then suburbs, then quarters as the map is zoomed in, the larger first and none written over another. The roads become a graph the window routes over itself, in milliseconds. **Use the sample region** loads a made-up stretch of coast instead, with no network needed.
2. **Place the network.** Pick a role above the map (supplier, port, warehouse, store, dark store or customer area) and click the map to place a site; keep clicking to place more, Escape to stop. A site snaps to the nearest road, and one more than 2 km from the roads loaded is ringed, as its legs are estimates. Click a site to open its card: its name, its role and its figures, each labelled where it comes from: the role's default (**assumed**), **yours** once changed, or **sourced** for a site adopted from public data. Goods are counted in pallets. A supplier ships 50 pallets a day and a store sells 5 until changed; a customer area takes a share of what is supplied by its population. A warehouse, store or dark store also has a **storage capacity** (empty: no limit) and a **stock cover**, the days of what it sends out or sells it aims to hold on top of what is on its way (3 days at a warehouse, 2 at a store, 1 at a dark store until changed); a warehouse also has its **holding cost** per pallet a day. A selected site also shows its name and **Delete** beside it on the map: type there to rename it (or click the site twice). Every action has a button or a menu item (right-click a site, a link or the map), a gesture on the map and a key (press **?** for the list): several sites can be selected (Shift-click, a box drawn with Shift, select all) and moved, duplicated or deleted together, and every change can be undone and redone (↶ ↷ above the map, or the usual keys). Keys and labels follow the platform: Ctrl and Delete on Windows and Linux, ⌘ and ⌫ on a Mac, where Control-click opens the menu. How the window treats newcomers, regular users and power users, on each platform, action by action: [docs/interaction.md](docs/interaction.md). Drag a site to move it. **Load your sites (CSV)** places a file of sites and their links; **Save your sites (CSV)** writes the network as one, keeping only the figures you set.
3. **Link it.** Links are suggested as sites are placed: each store, dark store and customer area from its nearest warehouse by road, and in a small network (up to 24 supply links) each warehouse from every supplier and port, so whatever the sources ship has somewhere to go; in a larger one each warehouse from its nearest four sources and each source to its nearest two warehouses. Suggested links are dashed and drawn along the roads they were routed over. Drag from a selected site's handle (or Shift-drag from any site) to another site to draw a link, click a link to select it, drag an end of a selected link to another site to move it and press Delete (or the card's button) to remove a site or a link. A link drawn into a site makes the suggested links into it yours too, and a suggested link you delete is not suggested again. The card lists what supplies a site and what it supplies, to add to from a list or take from with ✕, for those who prefer a list to a drag. A link that cannot be (a store supplying a warehouse, a supplier straight to a store in this version) is refused with the reason, on the map. Moving a site re-routes only its own links. The Network step lists what stops a build: a store with no warehouse, a warehouse with no source, two sites of one name, a vehicle that may not deliver to stores on a link to one.

    **Vehicles.** The Network step's **Vehicles** list is the catalogue every link chooses from: a heavy truck (30 pallets, 80 km/h, kept off store deliveries), a medium truck (12), a small truck (6) and a mini-van (2), each with its cost per kilometre and per day, top speed and loading time, all assumed until set from your own fleet, and whether it may deliver to stores and dark stores. Types can be added, renamed and deleted (the links on a deleted type go back to their usual vehicles). A link to a warehouse runs on heavy trucks, to a store on medium trucks and to a dark store on mini-vans, until another is chosen: on the link's card (with a second type if wanted, and how many of each: empty is as many as its flow needs, plus a reserve), from its menu (**Carry it by …**), or with **V**, which gives the selected links the next type; with several links selected the card sets them all. A link to a customer area has no vehicles: it stands for a parcel or courier service.
4. **Suggestions from public data, when asked for.** Each source is fetched only when its button is pressed, for the area loaded: **Ports** (OpenStreetMap port land, and each port's activity from [IMF PortWatch](https://portwatch.imf.org)), **Warehouses** (OpenStreetMap warehouses and industrial land) and **Towns as customer areas** (from the place names already loaded). What a source finds is shown as hollow sites on the map and a list with its coverage and notices; nothing joins the network until it is adopted, by a click on the map, **Adopt** in the list or **Adopt the top N**. An adopted site keeps what was found there. The discovery behind the suggestions is the earlier region import's:
    - **Ports.** A port the map leaves unnamed, or names after a single berth or jetty, takes IMF PortWatch's name once matched, and one PortWatch counts together with a neighbour (Los Angeles-Long Beach) takes their joint name. A major container port (1,000 container calls or more) that PortWatch places in the middle of port land tens of kilometres long, out of any one terminal's reach (Rotterdam), is matched to the largest commercial port within 20 km, which then stands for the whole port and takes its name. A port IMF PortWatch lists just outside the region, busier than any port in it, is named in a warning. A port hands inland its average container imports, converted at an assumed weight per TEU (10 t by default); PortWatch counts containers that only change ships there too, so the Model step sets both the weight of an imported TEU and the share that goes inland. Ports with no PortWatch match share an assumed 100 TEU/day each on average, in proportion to their port land, unless given a volume of their own. If PortWatch can't be reached, the ports are still suggested, with assumed volumes. Port activity data: Source: International Monetary Fund, free to reuse with that attribution.
    - **Warehouses.** Where warehouses are mapped densely, a cluster wider than 15 km is split into several zones, and a zone takes a building's name only when it reads as a logistics business; where few are mapped, industrial land stands in for them, and the notices say so.
    - **Towns.** Cities and towns come with their populations. A place mapped as a town with more than 250,000 people is not believed (the figure is most likely its district's) and takes the assumed size of a town, with a warning; one with fewer than 2,000 is kept and named in a notice. A city with mapped suburbs becomes several customer areas across it, each a cluster of nearby suburbs no more than 10 km across. A suburb belongs to the nearest city or town that reaches it (a city of millions reaches further), and a town with no population mapped inside a city, such as Deira in Dubai, counts as one of the city's suburbs. An area takes its suburbs' own populations where they are mapped, and an even share of the rest of the city's population otherwise, labelled as an assumption.
5. **Build the model.** The model is built from the sites and links: each supplier or port a source (a supplier is modelled, for now, as a port whose berths are its loading bays, shipping what it supplies whatever is ordered), each warehouse a warehouse with its storage capacity and cover, each link from a source to a warehouse a road lane on its vehicles, and each customer area a demand zone served by deliveries. A store or dark store holds stock: it is a stock room (a Warehouse node named "<store> stock", with its own capacity and cover), restocked over a road lane on its link's vehicles from each warehouse linked to it, and its shoppers (a demand zone of its name), who buy what is on the shelf within about two and a half hours and wait for what is not. A demand site linked to several warehouses draws on them in proportion to their size and nearness. A lane takes at least its length at its slowest vehicle's top speed, plus two hours at the gates from a source or one at the dock and the store's door, and never less than an hour and a half, the shortest trip the model's 15-minute steps follow faithfully (said where it applies). Its fleet of each type is the user's or sized to its flow with a reserve; a fleet set too small to keep up is warned about. Goods are counted in pallets until product categories come. A site that cannot hold what it hands on before it runs down (a warehouse with room for less than a day of what it sends out, a store with room for less than its shelves sell in two and a half hours) stops the build with the reason, and a storage capacity below the stock cover is said. Flows are balanced so every source ships what it supplies: the stores' own figures are scaled together to match, with a warning saying by how much, and a suggested supply link that would carry next to nothing is left out (drawn faint, and named) while every link you drew is built as drawn. The lanes take their times and distances from the window's routing, and every initial value is the steady state. **Port arrivals** chooses how a port matched to IMF PortWatch receives ships: **Follow PortWatch history** (the default) has each day's arrivals be the port's container imports on the matching day, over the latest days of its history (model day 0 is the first of them; the window says which dates), stored as a held schedule on the port's arrivals parameter, so ships queue at anchorage on the busy days; **Steady average** keeps them at the average, so the baseline holds still. Either way the average is taken over the days the run covers, so arrivals and demand balance. **History from** chooses those days: empty, the latest days are replayed (or the whole year fetched is averaged); a date, the model's days from it. When a port's history has a break, a month from which its container imports average less than half, or more than twice, what they did before, the window says so and offers the days **before it** (normal traffic) or **across it** (a month before, so the replay shows the break and what follows). **Fleet operator** (for a region built the earlier way; a network placed in the window runs on its own vehicle types, and the choice is hidden) chooses whose trucks run the lanes: none (each lane gets trucks of one size, enough for its flow with a reserve), **an invented operator** or **your own** (a JSON file of truck sizes with their costs per kilometre and per day, depots with their trucks, and the lanes it carries by origin and destination). An operator's truck sizes and costs become the region's; each depot's trucks are shared among its contracted lanes nearest to it, in proportion to what each needs. The invented one, labelled synthetic wherever it appears, carries about half the busiest port's flow inland from a depot at that port, with 40-foot and 20-foot trucks: enough for its lanes to keep up, with less spare than the toolbox gives a lane, so a closure or a surge makes its trucks the bottleneck first. The window warns when an operator's trucks can't keep up with a lane's flow from the start. The window lists every lane with its distance, hours and fleet of each vehicle type (and the operator's trucks, depots, costs and capacity against need), which warehouse serves each store and customer area, and where every value comes from: sourced, routed, assumed, synthetic or yours, the model-wide constants included. The map draws the lanes along the roads they were routed over, as corridors: a stretch of road several lanes share is drawn once, as thick as the containers a day it carries, and hovering it lists the lanes on it. A lane estimated rather than routed (no road route was found) is straight and dashed, and a standby lane, which carries nothing until cargo is diverted to its port, thin and dotted. The model opens in the canvas and, while **Keep the canvas in step** is ticked, follows every change made in the window.
6. **Run scenarios.** Once a model is built, the window forks it on the day a scenario starts and runs it beside the baseline. Four scenarios share the days they run for and a summary against the baseline: the share of orders delivered, the days an order waited on average (the time orders spent in the towns' backlogs over what was ordered: a closure every order outlasts still delivers them all, and this shows the delay), transport, fleet, holding and backlog costs since the scenario began, each port's longest anchorage wait, what the lanes it touches carried and how busy their vehicles were, each warehouse's lowest stock (and, with a storage capacity, how full it got), each store's lowest stock and the days its shelves were all but empty, and the most shoppers or customers left waiting. After a run the map shows what each road carried while the scenario lasted, at the scale of the model as built: red where it carried less than the baseline over the same days, amber where it carried more, dashed red where almost nothing moved; **Scenario** and **Baseline** above the map switch between the two. Every fork opens in the canvas.

    **Chokepoint.** Fewer ships through one of the 28 straits and canals IMF PortWatch follows: choose the chokepoint, the cut, the day it starts and how long it lasts. Each kept port loses its share of ships through that chokepoint times the cut. PortWatch does not say which ports depend on which chokepoint, so the shares come from geography and are yours to change: a port in the Persian Gulf receives all its ships through Hormuz, one in the Black Sea through the Bosporus, one in the Sea of Azov through Kerch and the Bosporus, and one in the Red Sea half through Suez and half through Bab el-Mandeb; every other port starts at none. The window also shows the chokepoint's container ships a day lately against its busiest full year, from PortWatch, and can use that drop as the cut, or, for each port the chokepoint reaches whose history has a fall, that port's own fall (over its share through the chokepoint), often the better cut for one port, since some ships still come. If a port the disruption reaches is already modelled at less than half its traffic before a break, the period chosen may be the disruption itself, so the window warns that a cut would count it twice and asks before running. The cargo kept out is lost by default (diverted or cancelled), and while the cut lasts the warehouses stop ordering it: an order for cargo that will not come would count as on its way and hold back their orders from every other port; a share of it can instead arrive later, evenly over a number of days after the disruption ends, on top of the usual traffic, so the berths may queue ships while the backlog clears. The fork starts on the disruption's first day, follows each port's arrivals (its history or its average) scaled for the chosen days, and the window also lists, for each port, the containers kept out, how many of them arrived later and how many never did. A share of the cargo kept out can instead be **diverted** to a kept port outside the chokepoint, or shares to two of them, each with its own berths, as ships that can't reach a port in the Persian Gulf land at an east-coast port and their cargo is trucked inland: from the disruption's first day that port's arrivals rise by the diverted cargo, each warehouse that ordered from a port the cut reaches orders the matching share from it instead, and its lanes hire trucks for it (all it needs, or the share found) over the hiring time. Where a warehouse has no lane from that port, the model is rebuilt with a **standby lane**: routed, with no flow and no trucks in the baseline, so the baseline is unchanged. The port's berths keep the capacity the model gives them (sized for what it usually hands inland), so cargo diverted beyond it waits at its anchorage; a port that is mostly transhipment may have far more, and its berths' capacity can be given, from the disruption's first day to the end of the run. Diverting more than a port's berths can take is worse than losing the cargo: the warehouses order it from that port, and it never gets through. **Demand while the cut lasts** changes every town's orders by a percentage for the same days (0 unless set), for people who buy less, or stock up, in a crisis; nothing published says by how much, so the figure is the user's.

    **Road closure.** A lane closed (or open only part of the way) for a while, and what its trucks do meanwhile. **Wait for it to reopen**: the lane loads only its open share, the warehouse orders over it only that share (orders placed on a closed road would count as on their way, and its order rule would then cut its orders on its open lanes too), and the cargo waits in its port's yard; the warehouse lives on its stock and its other lanes, and trucks already on the road finish their trips. **Take a detour**: the lane stays open, but every trip takes the hours given longer each way, over proportionally more kilometres, so more trucks are on the road and each trip costs more. **Order from the warehouse's other ports**: what the lane can't take is ordered over the warehouse's other lanes, which ship only what their own ports hold; the closed lane's cargo still waits at its port, and orders left with the other ports hold the warehouse's own lane back after the road reopens, so this is often the worst of the three.

    **Fleet.** The vehicles on every lane, on every lane a type runs on (mini-vans short, say), on one lane, or on the operator's lanes, changed by a percentage (drivers short, or more hired): each size is hired or released towards the new number over the hiring time, and only idle vehicles are released.

    **Demand.** Every store's, dark store's and customer area's demand, or one's, raised (or lowered) by a percentage for a while, as on peak days.

**Sessions are kept with the project.** The window keeps its session with the open project after every change, and each build stores it with the model it opens in the canvas (a network placed and not yet built is saved with the project too): the place, the road level, the sites and links (routed again on reopening, over the same roads), the suggestions asked for, the last build's tables, and the map data it was fetched from, with each file's address and date. A session kept by the earlier curation workflow reopens with its kept sites as pins, linked as suggested. Saving the project saves the session; a save made while a change is still on its way from the window (Show in Konjugate, or Keep the canvas in step on a large model) waits for it. Opening the project and then the toolbox carries on where it was, with no network needed. Load the roads again for newer data. This needs a Konjugate that supports `projectSession`, `keepSession` (a session kept before any model is built), `fetchCache` (fetches kept on disk), `parameterSchedules` (stored parameter schedules), `scenarioForkTime` (a fork the window times) and `suppliedPerParameter` (one scenario changing several parameters along their own paths).

The map is drawn from the fetched data itself (an add-on window shows no map tiles). Under it, faintly, are land, coastlines and country borders from [Natural Earth](https://www.naturalearthdata.com) (1:10m, public domain), bundled with the add-on so they need no fetch: a border Natural Earth classes as an international boundary is solid, and one it classes otherwise (disputed, indefinite, a line of control, a claim or breakaway line) is dashed, as Natural Earth's default view draws them. At 1:10m they are good to about a kilometre, so a coast may sit a little off the OpenStreetMap ports on it. The sample region is drawn without them. Map data © OpenStreetMap contributors, ODbL.

How it works: `packages/toolbox/lib/` holds the pipeline:

- `overpass.mjs`: the queries;
- `discovery.mjs`: candidates, clustering, ranking and coverage (the suggestions);
- `roadGraph.mjs`: the road graph, and the router the earlier curation workflow uses;
- `routing.mjs`: the window's router: the graph compacted between junctions, snapping through a grid, A* for one leg and one pass for the nearest of several sources;
- `network.mjs`: the sites and links the user places: roles and their defaults, suggested links, what stops a build and what the importer builds from;
- `vehicles.mjs`: the vehicle catalogue, each link's vehicles and what may carry what;
- `corridors.mjs`: the roads the lanes share, for the map;
- `regionModel.mjs`: the model, from the user's links (stores with stock rooms, lanes on their vehicle types, in pallets) or, for the earlier workflow, by gravity;
- `operator.mjs`: a fleet operator, read, allocated to lanes or invented;
- `scenarios.mjs`: the paths a road closure, a fleet change and a demand surge follow (a chokepoint's are in `chokepoints.mjs`);
- `sites.mjs`: the CSV, read and written;
- `mapData.mjs`: what the map draws;
- `geography.mjs`: the bundled Natural Earth tiles, cut to a region.

`importers/region.mjs` runs the pipeline for the window in steps: roads (the map and the compacted road graph), discover with the sources asked for (the suggestions), sites (a CSV) and buildNetwork (the model); and, for the live region check and the engine tests, the earlier workflow's discover and build.

## Development

This repository sits next to a Konjugate checkout (`../konjugate`, or set `KONJUGATE_DIR`). It needs a Konjugate recent enough to support node-template parameters and to settle algebraic states before the first step, with its engine built (`npm run build:engine` there). The scripts use Konjugate's own package, validation and project-file code, so what passes here is what the app accepts.

- `npm run build` builds the plugin into `out/konjugate.logistics.engine-<version>.kjp`, with the example model, its guide and its thumbnail, and the toolbox add-on into `out/konjugate.logistics.toolbox-<version>.kja`, with its own copy of the templates and the sample region. The version comes from `package.json`.
- `npm run build:models` writes the example models to `models/`, so a model's structure is reviewable in git.
- `npm run generate:example-thumbnails` opens each example in the real app and saves its preview to `thumbnails/`. Run it when an example's layout changes.
- `npm run install:dev` builds, then installs into your local Konjugate's `userData/packages` (override with `KONJUGATE_USER_DATA`).
- `npm test` runs the unit tests: every template passes Konjugate's template validator, every per-day rate goes through `secondsPerDay`, and shared constants agree across templates; the routing agrees with the full road graph and with plain Dijkstra, and routes a city of 40,000 road nodes in milliseconds; links are suggested, kept, refused and dismissed as described; vehicle types are chosen, defaulted and refused as described; the importer's steps load roads alone, suggest only the sources asked for and build a model whose lanes are the network's links, with stores that hold stock, lanes on the vehicles each link names and a port's containers counted as pallets.
- `npm run test:engine` runs four models through the engine CLI (or, with `KONJUGATE_ENGINE=export`, as Konjugate's code export writes them, a Python program that follows the engine step for step, for a machine with no engine build of its own; Python 3 is all it needs):
    - a port network built from the templates (`scripts/portNetwork.mjs`), in five scenarios: a steady baseline, a berth outage, a truck shortage, rail relief and fleet hiring;
    - a model built by region import from a made-up region (`tests/fixtures/syntheticRegion.mjs`), in its baseline, a berth outage and arrivals that follow a PortWatch history; and, with an invented operator, a baseline that holds still, a road closed three ways (trucks waiting, on a detour, orders sent to another port), the operator's trucks halved and a demand surge;
    - a network placed as a user places it (`tests/engine/networkModel.mjs`): three suppliers, two warehouses, twenty stores, a dark store and a customer area on an invented city grid, linked as suggested, in its baseline, a demand surge at one warehouse's stores and its busiest supply lane closed;
    - the same kind of network with its vehicle catalogue (`tests/engine/vehicleNetwork.mjs`): stores with stock rooms, lanes on heavy trucks, medium and small trucks and mini-vans, and a warehouse with little room; its baseline holds still in pallets, a store whose only lane closes runs out while its neighbour keeps its stock, a big store's vans cut by three quarters run it down, and the small warehouse orders less under a surge than it would with no limit.

  Each run must conserve goods and vehicles, keep every warehouse's and stock room's on-order count equal to what its lanes hold, and match the figures worked out by hand.
- `node scripts/liveRegionCheck.mjs --place "<place>" [--radius 40] [--run]` (or `--bbox south,west,north,east`) runs region import on real OpenStreetMap data. It fetches from the public Overpass server, caches the answers in `out/regionCache/`, and prints the coverage report, the candidates and the model. With `--run`, it also checks that the model's baseline holds still, or with `--arrivals history`, that each matched port's arrivals follow its PortWatch history. It lists the chokepoints the kept ports depend on with their recent transits, `--from 2025-10-01` chooses the history period, and with `--disrupt chokepoint6:50:10:30` (the chokepoint, the cut in percent, the first day and the number of days, and optionally `:60:20` for 60% of the cargo kept out arriving over the 20 days after) it also runs that disruption; `--tonnes-per-teu` and `--inland-share` set the conversion and compares it with the baseline. `--operator synthetic` (or a path to your own operator's JSON) adds a fleet operator, and with `--run --scenarios` it runs a month under each of the window's scenarios (the chokepoint the kept ports depend on most cut by half, the busiest lane closed with its trucks waiting and then on a detour, the operator's trucks cut by 30%, demand up 30%), prints the share of orders delivered, the road cost, the lowest stock, the highest backlog and the longest anchorage wait against the baseline, and checks that every input is labelled. Parts already fetched are kept, so a run stopped by an overloaded server continues where it left off; `--overpass <host>` uses another public Overpass server, such as `overpass.private.coffee`.
- `npm run test:window` drives the toolbox window in a plain browser (Playwright from the Konjugate checkout), with a stand-in for Konjugate's host that runs the importer as the host does, within its limits on what goes in and out (`tests/window/host.mjs`): pins placed from the palette, links suggested, drawn, refused and deleted, a moved site re-routing only its own links, a warehouse's storage capacity, the vehicle catalogue edited and a link's vehicles chosen on its card, from its menu and with V, a build, suggestions only when asked for, the CSV saved and loaded, the session restored and an earlier session migrated and a searched region fetching its roads alone. No engine runs, so it needs no Konjugate build; with `KONJUGATE_ENGINE=export` it also runs a road closure to a store as Konjugate's code export writes the model, and checks the summary shows the store running out.
- `node scripts/routingCheck.mjs` times the routing on a real region cached by the live region check: the graph compacted, snapping, one leg, the nearest-source pass and a moved store re-routed.
- `npm run test:interaction` launches the real Konjugate app with a scratch user-data directory (never yours) and installs the built packages. It uses Playwright from the Konjugate checkout. It runs two tests:
    - **`tests/interaction/run.mjs`** builds a network through the UI: placing nodes, applying bundles and editing shared parameters. It checks the saved project against the same network built by script, and the app's run against the engine CLI. It then opens the example from the Examples dialog, forks it as the guide describes, and checks the guide's claims.
    - **`tests/interaction/regionWindow.mjs`** drives the toolbox window offline, with the network answered from the synthetic region: the sample region, a place search and Load roads (the roads and place names alone), ports, warehouses and towns suggested only when asked for and adopted, a port's volume on its card, Build (checked against the canvas), dragging a warehouse (its lanes are rerouted), a customer area placed on the map (it is served), a chokepoint disruption (counted in pallets), the lanes on heavy trucks, a road closure and a detour, a cut in heavy trucks and a demand surge, and the session restored from the saved project with no network.

  On Linux without a GPU, pass Electron flags through `KONJUGATE_ELECTRON_ARGS`, for example `--no-sandbox --use-gl=angle --use-angle=swiftshader`.

`node scripts/buildGeography.mjs` cuts Natural Earth's 1:10m land, coastline and country borders (at a pinned release, downloaded once into `out/naturalEarth/`) into 10-degree tiles in `packages/toolbox/geography/`, which are committed; they add about 2 MB to the add-on. Run it when the Natural Earth release changes.

`scripts/templatePlacement.mjs` places templates the way the app does, so tests and models built by script run exactly what the templates say.
